# Rule coverage: runtime schemas

What `protoc-gen-strict-schema` emits, which `buf.validate` rules each target
enforces, and what it leaves to protovalidate.

← [Rule coverage](rule-coverage.md) · [README](../README.md)

## What it emits

A second plugin binary. Where `protoc-gen-strict` narrows types, this one emits
schemas that check a JSON value at runtime, from the same rules:

- **`target=json`**: a JSON Schema 2020-12 module per `.proto`, on top of the
  bundles of the official generator, protoschema-plugins' protoc-gen-jsonschema,
  which the plugin runs itself and writes under `jsonschema/`. At import time
  the module removes every keyword that rejects values protovalidate accepts.
- **`target=zod`**, **`target=zod3`**: a Zod 4 or Zod 3 module per `.proto`,
  generated from the rules. A rule becomes a native Zod check when a Zod
  built-in does exactly what protovalidate does. protovalidate-es checks every
  other rule, inside the schema of the field it belongs to.

protovalidate-es is the reference. It passes the same conformance suite as
protovalidate-go, so a check in the client agrees with the server. Both targets
describe canonical protojson, the form protobuf-es `toJson()` writes.

Every module is written as TypeScript by default. `output=js+dts` writes it as
JavaScript with declaration files instead: the same code without its types, so
a JavaScript project gets the same schemas and a TypeScript one importing it
the same checks. The generator writes the `.d.ts` itself; `make verify` checks
it matches what tsc infers for the `.ts`. `import_extension=js` makes the
imports resolvable by Node's ESM loader.

Install, `buf.gen.yaml` and options:
[protoc-gen-strict-schema](../cmd/protoc-gen-strict-schema/README.md).

## Target `json`

### `<message>JsonSchema`

One per top-level message, the only kind protoschema-jsonschema bundles. For
[`proto/example/v1/user.proto`](../proto/example/v1/user.proto), trimmed:

```ts
// Code generated by protoc-gen-strict-schema. DO NOT EDIT.
// source: example/v1/user.proto

import addressBundle from "../../jsonschema/example.v1.Address.jsonschema.bundle.json" with { type: "json" };
import userBundle from "../../jsonschema/example.v1.User.jsonschema.bundle.json" with { type: "json" };
import { loosen } from "../../strict/jsonschema";

// … addressJsonSchema

/**
 * User demonstrates standard buf.validate rules alongside custom CEL rules.
 *
 * JSON Schema 2020-12 for example.v1.User, from protoschema-jsonschema.
 *
 * Left to runtime validation:
 *   id
 *     cel[user.id.prefix]: this.startsWith('usr_')
 *       message: id must start with 'usr_'
 *       refs: this
 *       calls: startsWith
 *   email
 *     string.email = true
 *   display_name
 *     string.pattern = ^[a-zA-Z0-9_ ]+$
 *   login_count
 *     cel[this >= 0]: this >= 0
 *       refs: this
 *       calls: _>=_
 *   roles
 *     repeated.unique = true
 *   absent fields
 *     id, display_name, age, login_count, roles: an absent key is the zero value, which the rules still apply to
 */
export const userJsonSchema = loosen(userBundle);
```

- The value is the bundle after `loosen`: a JSON Schema 2020-12 document with
  local `$ref`s only. Hand it to a 2020-12 validator.
- The doc comment names every rule the schema does not carry: the ones whose
  keyword `loosen` removed, the ones whose keyword is looser than the rule, and
  the ones upstream never writes. It is the same "Left to runtime validation"
  contract the overlays keep.
- protojson omits an implicit field holding its zero value, so an absent key is
  `""`, `0` or `[]`, and protovalidate still applies the field's rules to it.
  No keyword of the schema sees an absent key, so the comment names those
  fields under "absent fields". A field with a mandatory key is not among them.
- A nested message has no export of its own. Its rules are listed in the
  comment of the top-level message that declares it, prefixed:
  `Address.country_code` under `warehouseJsonSchema`.

The bundles come from protoc-gen-jsonschema, run by the plugin over the same
request with `target=json-bundle`. A plugin never sees another plugin's output,
so this is what lets the run check them: the generation fails, with the reason,
when the executable is not on the `PATH`, reports a version other than
`v0.6.0`, the one the table below mirrors, fails, or writes no bundle for a
top-level message a `.schema` module imports.

Why `json-bundle` rather than another protoschema-jsonschema target:

- `json` uses the JSON (camelCase) property names protojson emits.
- `bundle` makes each schema self-contained.
- Not `strict`, which requires implicit default values to be set explicitly;
  protojson omits them. The lenient variant accepts what protojson parsers
  accept: the proto name as an alias, through `patternProperties`, and numbers
  written as strings.
- `additional_properties` stays at its default, `false`, as protobuf-es
  `fromJson` rejects unknown fields.

### `loosen` and `fixesTable`

`strict/jsonschema.ts` holds one table, keyed by `$defs` id and then by the
field's JSON name, `""` for the def itself. Each entry names the rule or shape
that makes its keyword wrong. From the fixtures:

```ts
export const fixesTable: Fixes = {
  "example.v1.User.jsonschema.json": {
    // string.email
    "email": { fixes: [{ drop: ["format"] }] },
    // string.pattern
    "displayName": { alias: "display_name", fixes: [{ drop: ["pattern"] }] },
  },
  // …
  "google.protobuf.Duration.jsonschema.json": {
    // google.protobuf.Duration: format is ISO 8601, protojson writes "1.5s"
    "": { fixes: [{ drop: ["format"] }] },
  },
  // …
  "shop.schema.v1.CollectionCoverage.jsonschema.json": {
    // repeated.items.string.uri
    "links": { fixes: [{ at: "items", drop: ["pattern"] }] },
    // map.values.string.uri
    "labels": { fixes: [{ at: "additionalProperties", drop: ["pattern"] }] },
    // map<bool, _>: JSON keys are strings
    "flags": { fixes: [{ drop: ["propertyNames"] }] },
  },
  // …
};
```

`loosen(bundle)` returns a copy with the table applied:

- It deep-copies first. Every importer of a JSON module shares one object, so
  the import is never mutated.
- For each def in `fixesTable` that the bundle's `$defs` holds, it finds the field
  under `properties` and, where the proto name differs, under its lenient alias
  `patternProperties["^(proto_name)$"]`.
- `at` moves the fix to the field's `items`, `propertyNames` or
  `additionalProperties`.
- It deletes the keywords there and in every `anyOf` branch below.
- A def or field the bundle lacks is skipped, as a field hidden with
  `jsonschema:ignore` legitimately is.

The table covers every message a generated file's bundle can reach, imported
files included. The rule-to-verdict mapping behind it is one Go table,
`internal/generator/schemagen/jsonfixes.go`, which mirrors
protoschema-jsonschema v0.6.0. It is the one place to update when upstream
changes.

### What upstream writes, and what `loosen` does with it

- **keep**: the keyword is exact. The rule is carried, and not named.
- **keep, named**: the keyword stays and accepts more than protovalidate. The
  rule is named under "Left to runtime validation".
- **remove**: the keyword rejects values protovalidate accepts, or does not
  compile. `loosen` deletes it, and the rule is named.
- **runtime**: upstream writes nothing. The rule is named.

`format` is validator-defined in JSON Schema 2020-12: an annotation unless the
validator asserts it, and every validator ships its own grammar. The Zod
behaviour quoted below is one concrete implementation.

**String formats**

| Rule | protoschema-jsonschema writes | Verdict | Valid value it rejects |
|---|---|---|---|
| `hostname` | `pattern` | remove | `example.com.` |
| `ip` | `pattern`, without zone ids or an embedded IPv4 | remove | `fe80::1%eth0`, `::ffff:192.0.2.1` |
| `uri`, `uri_ref` | a simplified `pattern`, with a `\#` escape that is a syntax error under the `u` flag ajv sets | remove | `mailto:a@b.io`, `urn:isbn:1`, `https://user@example.com/`, `http://[::1]/`; under ajv the schema does not compile at all |
| `address` | the hostname and IP patterns | remove | `example.com.` |
| `host_and_port` | `pattern`, port `[1-9]…` | remove | `example.com:0` |
| `ip_with_prefixlen`, `ipv6_with_prefixlen` | `pattern` | remove | `::ffff:192.0.2.1/96` |
| `ip_prefix`, `ipv4_prefix`, `ipv6_prefix` | `pattern`: a literal `0` or `::` for the host bits | remove | `10.0.0.128/25`, `2001:db8:0:0:0:0:0:0/32` |
| `email` | `format: email` | remove | `user@localhost`, `a!b@x.io` under Zod's `z.email()` |
| `ipv6` | `format: ipv6` | remove | `fe80::1%eth0` under Zod's `z.ipv6()` |
| `ipv4` | `format: ipv4` | keep, named | — |
| `ipv4_with_prefixlen` | `pattern`, which admits leading-zero octets | keep, named | — |
| `uuid`, `tuuid` | protovalidate's own regex, unless a `pattern`, `prefix`, `suffix` or `contains` on the same field overwrote it | keep; named when overwritten | — |
| `well_known_regex` HTTP header name, with `strict: true` set explicitly | `pattern`, with a `\'` escape that is a syntax error under the `u` flag ajv sets | remove | none: it does not compile |
| `well_known_regex` otherwise, `strict`, `ulid`, `protobuf_fqn`, `protobuf_dot_fqn` | nothing | runtime | — |

**String length and content**

| Rule | protoschema-jsonschema writes | Verdict |
|---|---|---|
| `min_len`, `max_len`, `len` | `minLength`, `maxLength`. JSON Schema counts code points, as protovalidate does | keep |
| `const`, `in` | `enum` | keep. `in` next to `const` is named: upstream writes the `const` |
| `max_bytes` | `maxLength`. A string has no more code points than UTF-8 bytes | keep, named |
| `len_bytes` | `maxLength` set to `max_bytes`, which is 0 when unset: every non-empty string fails | remove, unless `max_bytes`, `len` or `max_len` sets that `maxLength`. Named either way |
| `pattern` | the RE2 source as an ECMA-262 `pattern`. `(?i)` and `(?P<n>…)` are syntax errors; `\s` matches U+00A0 in ECMA-262 only | remove |
| `prefix`, `suffix`, `contains` | a regex built without escaping: `prefix: "+1"` gives `^+1.*`, and `.` does not cross a line break | remove |
| `min_bytes`, `not_in`, `not_contains` | nothing | runtime |

A field with a well-known format and `pattern`, `prefix`, `suffix` or `contains`
keeps only one `pattern` upstream. Removing it leaves all of those rules to
runtime validation.

**`required`**

A field has presence when it is labelled `optional`, sits in a oneof, or is a
message. Every other field is implicit: protovalidate reads its zero value as
unset.

| Field | protoschema-jsonschema writes | Verdict |
|---|---|---|
| with presence | the field in the parent's `required` | keep. When the field carries another rule of its type, upstream also writes `minLength: 1` where no length rule did; that keyword is removed: a set field may hold `""` |
| implicit `bool`, enum | the field in the parent's `required`, the zero value excluded | keep |
| implicit `string`, `bytes` | the field in the parent's `required`, and `minLength: 1` only when the field carries another rule of its type | keep with such a rule; named without one: `""` passes |
| implicit number, `repeated`, map | the field in the parent's `required` | keep, named: `0`, `[]` and `{}` pass |

With `ignore` set, `required` is always named.

**Other types**

| Case | protoschema-jsonschema writes | Verdict |
|---|---|---|
| every `bytes` value: a field, a list item, a map value, `BytesValue` | `pattern` `^[A-Za-z0-9+/]*={0,2}$`, which rejects the URL-safe base64 protobuf-es decodes | remove |
| `bytes.len`, `min_len`, `max_len` | bounds on the base64 length | keep, named |
| other `bytes` rules | nothing | runtime |
| `google.protobuf.Duration`, every field | `format: duration`, ISO 8601 (`PT1.5S`); protojson writes `"1.5s"` | remove, from the def |
| `google.protobuf.Timestamp` | `format: date-time`, validator-defined: ajv-formats checks the calendar date, protobuf-es's parser does not | keep |
| rules on a message-typed field: Timestamp, Duration, Any, FieldMask, wrappers, any other message | a `$ref` to a def that carries none of them | runtime |
| `map<bool, V>` | `propertyNames: {type: boolean}`; JSON object keys are always strings | remove `propertyNames` |
| `map.min_pairs`, `max_pairs` | nothing | runtime |
| `map.keys`, `map.values`, `repeated.items` rules | the scalar's keywords, under `propertyNames`, `additionalProperties` or `items` | as the scalar |
| `repeated.min_items`, `max_items` | `minItems`, `maxItems` | keep |
| `repeated.unique` | nothing | runtime |
| int32-family `gt`, `gte`, `lt`, `lte`, `const`, `in` | on the number branch of an `anyOf`; the string branch, which protobuf-es also parses, is unbounded | keep, named |
| int32-family `not_in` | nothing | runtime |
| int64-family rules | on the number branch only; the canonical form is a string | keep, named |
| `double` rules | mapped, `NaN` and `±Infinity` included | keep, named |
| `float` bounds, `const`, `in` | the float32 bound as its shortest decimal (`maximum: 0.1`); protojson writes the float32 widened to a double (`0.10000000149011612`), which that rejects | remove the numeric keywords at that position |
| `float.finite` | the `NaN` and `±Infinity` strings left out | keep, named |
| `bool.const` | `enum` | keep |
| enum `const`, `in`, `defined_only` | a filtered `anyOf` of names and numbers | keep |
| enum `not_in` | the names filtered; the numbers only when `const`, `in` or `defined_only` is also set | keep; named without one of those |
| `ignore: IGNORE_IF_ZERO_VALUE` on the field, any rule | the keywords, as if `ignore` were unset: the zero value fails | remove every rule keyword of the field itself |
| a member of a `(buf.validate.message).oneof` that sets no `ignore` | the keywords; protovalidate gives such a member `IGNORE_IF_ZERO_VALUE`, which upstream does not know | as `IGNORE_IF_ZERO_VALUE` |
| `ignore: IGNORE_ALWAYS` on the field | nothing | runtime |
| `ignore` of any value under `repeated.items`, `map.keys` or `map.values` | the keywords: upstream reads `ignore` on the field only | remove every rule keyword at that position |
| `ignore: IGNORE_ALWAYS` on a message field, list items or map values of a message type | a `$ref` to the message's def, whose keywords still apply though protovalidate never evaluates the message | remove the `$ref`: the value accepts anything |
| a field hidden with `// jsonschema:hide` | the field under `patternProperties["^(jsonName|proto_name)$"]` instead of `properties` | fixed there like any other field |
| field CEL, message CEL, oneofs | nothing | runtime |

A reversed int32 range (`gt: 10, lt: 5`, "outside 5..10") comes out as two
number branches, exact for numbers.

`loosen` only removes keywords, so a few over-narrowings stay, documented as
deliberate the way the README documents the enum zero member:

- int32-family values written as numeric strings in a non-decimal form, such as
  `"1e2"` or `"1.0"`. protobuf-es parses them with `Number()`; the string
  branch's `^-?[0-9]+$` rejects them.
- JSON `null`. protobuf-es reads it as unset; the schema admits no `null` type.
  That includes a `google.protobuf.NullValue` field, whose only JSON form is
  `null`.
- A required field written under its proto name. The parent's `required` lists
  the JSON name only, though the lenient schema otherwise accepts the proto name
  as an alias.
- An enum number that `in` or `const` allows but the enum does not declare.
  Upstream builds the number ranges from the declared members; protovalidate
  accepts the number, as an open enum does.

## Targets `zod` and `zod3`

### What `<file>.zod.ts` exports

For [`proto/example/v1/user.proto`](../proto/example/v1/user.proto), target
`zod`, trimmed:

```ts
import { z } from "zod";
import { field, message, register } from "../../strict/protovalidate";
import { AddressSchema, UserSchema, file_example_v1_user } from "./user_pb";

register(file_example_v1_user);

// … addressZodObject, addressZod

export const userZodObject = z.strictObject({
  /**
   * string.max_len = 64
   * string.min_len = 5
   * cel[user.id.prefix]: this.startsWith('usr_')
   *   message: id must start with 'usr_'
   *   refs: this
   *   calls: startsWith
   *
   * Carried by Zod: string.max_len, string.min_len.
   * Checked by protovalidate: cel[user.id.prefix].
   */
  id: z.string().max(64).min(5).superRefine(field(UserSchema, "id", ["string.max_len", "string.min_len"])).optional(),
  // …
  roles: z.array(z.string().min(1)).min(1).superRefine(field(UserSchema, "roles", ["repeated.items.string.min_len", "repeated.min_items"])).optional(),
  address: addressZod.optional(),
});

/**
 * Full validation of example.v1.User. Adds what protovalidate checks on the whole message:
 *   the rules of id, display_name, age, login_count, roles when absent: protojson omits a zero value
 */
export const userZod = userZodObject.superRefine(message(UserSchema));
```

- **`<message>ZodObject`** is a `z.strictObject`, keyed by JSON name. Each field
  schema carries that field's rules, so a part taken out of it keeps validating.
  It does not carry the rules that span the message, so it is not a full
  validator by itself.
- **`<message>Zod`** is the schema to parse with. It is `<message>ZodObject`
  itself when the message has nothing for `message()` to check, and
  `<message>ZodObject.superRefine(message(desc))` otherwise. Its doc comment
  lists what the refinement adds.
- **`<enum>Zod`** is a `z.enum` of the member names, the zero member included.
- Every message gets both schemas, nested ones included. A message is written
  after the messages its fields name: `Address` comes first, though the proto
  declares it after `User`.
- A message-typed field references the other message's `<message>Zod`, from this
  module or another generated one, so a nested message is validated in full. A
  message from a file this run does not generate has no Zod module: the field is
  `z.unknown()`, with a `field()` that checks it decodes, and its doc comment
  says so.
- Names are protobuf-es's, in camelCase: `Warehouse_Address` gives
  `warehouseAddressZod`. Two types of one file that fold to the same name,
  `Order.Status` and `OrderStatus`, are told apart by a `$1` on the later one,
  enums after messages.
- Each field's doc comment lists its rules and who enforces each: "Carried by
  Zod" for the native checks, "Checked by protovalidate" for the rest.
- Types come from Zod: `z.infer<typeof userZod>`. No separate type is exported.

`<file>.zod3.ts`, for `zod3`, imports `zod/v3` and differs on the string
lengths, which move into `field()`:

```ts
  id: z.string().superRefine(field(UserSchema, "id")).optional(),
```

### Composing

Compose from `<message>ZodObject`. Each part keeps its own rules:

```ts
import { z } from "zod";
import { userZod, userZodObject } from "./gen/typescript/example/v1/user.zod";

const user = userZod.parse(json); // every rule, the message-wide ones included

const Invite = z.strictObject({ email: userZodObject.shape.email, note: z.string() });
const Profile = userZodObject.pick({ displayName: true, roles: true });
const Member = userZodObject.extend({ team: z.string() });
```

`Invite` still requires a well-formed email; `Profile` still sends `roles`
through protovalidate for `repeated.unique`. What a composed schema does not
have is `message()`: message CEL, oneofs, and the rules of absent fields.

Do not compose from `<message>Zod`:

- **Zod 4.** It is a `ZodObject` with a refinement. `.shape` works; `.pick()`,
  `.omit()`, `.partial()` and an `.extend()` that overwrites a key throw. An
  `.extend()` that adds a key keeps `message()`, whose `fromJson` then rejects
  the new key as an unknown field.
- **Zod 3.** `.superRefine()` returns a `ZodEffects`, which has no `.shape`,
  `.pick()` or `.extend()`.

### JSON shape

The schemas describe canonical protojson: the form protobuf-es `toJson()` emits,
and its `json_types=true` `<Message>Json` types describe.

| Proto | Zod |
|---|---|
| `int32`, `uint32`, `sint32`, `fixed32`, `sfixed32` | `z.number().int()` |
| `int64`, `sint64`, `sfixed64` | `z.string().regex(/^-?[0-9]+$/)` |
| `uint64`, `fixed64` | `z.string().regex(/^[0-9]+$/)` |
| `float`, `double` | `z.union([z.number(), z.enum(["NaN", "Infinity", "-Infinity"])])` |
| `bool` | `z.boolean()` |
| `string`, `bytes` | `z.string()` |
| enum | `<enum>Zod`, the member names. An enum from a file this run does not generate is written out as a `z.enum` |
| message | `<message>Zod`; `z.unknown()` for a message this run does not generate |
| `repeated T` | `z.array(T)` |
| `map<K, V>` | `z.record(z.string(), V)` |
| `Timestamp`, `Duration`, `FieldMask` | `z.string()` |
| `Struct`, `ListValue` | `z.record(z.string(), valueZod)`, `z.array(valueZod)` |
| `Value` | `z.json()`; in Zod 3, which has none, a `z.lazy()` union typed `z.ZodType<JsonValue>` |
| `NullValue` | `z.null()` |
| `Any` | an object with an optional `"@type"` that keeps its other keys: `z.looseObject`, `.passthrough()` in Zod 3. An empty `Any` is written as `{}` |
| `Empty` | `z.strictObject({})` |
| wrappers (`StringValue`, …) | the wrapped scalar's schema |
| field without `required` | `.optional()` |

The well-known types come from `strict/wkt.zod.ts`, `strict/wkt.zod3.ts` for
`zod3`.

protojson parsers accept the forms below; these schemas reject them. They are
documented as deliberate, the way the README documents the enum zero member:

- proto names as JSON keys (`display_name`): `z.strictObject` knows only the
  JSON names;
- enum values written as numbers;
- `int32` written as a string, `int64` written as a number;
- `float` and `double` written as numeric strings (`"1.5"`);
- `null` for an unset field. `Value` and `NullValue` accept `null`: it is their
  value.

### Native checks and protovalidate

A rule becomes a native Zod check only when a Zod built-in implements exactly
what protovalidate does. A fixed regex that protovalidate-es itself evaluates
with the platform `RegExp` counts as exact when it is copied verbatim. Every
other rule goes through `field()`.

| Rule | `zod` (4.6) | `zod3` |
|---|---|---|
| `required`, field with presence | the key is not optional | same |
| `required`, implicit `string` | the key is mandatory, and `.min(1)` | same: one UTF-16 unit is at least one code point |
| `required`, implicit `bool` / enum / `repeated` | `z.literal(true)` / the member names without the zero member / `.min(1)` | same |
| `required`, implicit number, `bytes`, map | the key is mandatory; the zero value is left to `field()` | same |
| `string.const` / `string.in` | `z.literal` / `z.enum` | same |
| `string.prefix` / `suffix` / `contains` | `.startsWith()` / `.endsWith()` / `.includes()` | same |
| `string.min_len` / `max_len` / `len` | `.min()` / `.max()` / `.length()`, which count code points since Zod 4.5 | `field()`: Zod 3 counts UTF-16 units |
| `string.uuid`, `tuuid`, `ulid`, `protobuf_fqn`, `protobuf_dot_fqn`, `email` | `.regex()` with protovalidate-es's constant | same |
| int32-family `gt` / `gte` / `lt` / `lte` | `.gt()` / `.gte()` / `.lt()` / `.lte()` | same |
| int32-family `const` / `in` | `z.literal` / a union of `z.literal` | same |
| enum `const`, `in`, `not_in`, `defined_only` | a filtered `z.enum` of member names | same |
| `bool.const` | `z.literal` | same |
| `repeated.min_items` / `max_items` | `.min()` / `.max()` | same |
| `repeated.items` rules | the element's check, by the rows above | same |

Where `const` or `in` is set on a string or int32-family field, the schema is
that literal or enum, and the field's other rules go through `field()`.

These go through `field()`:

- `min_bytes`, `max_bytes`, `len_bytes`;
- `pattern`, which is RE2;
- `hostname`, `ip`, `ipv4`, `ipv6`, `uri`, `uri_ref`, `address`,
  `host_and_port`, and every `*_with_prefixlen` and `*_prefix` format;
- `well_known_regex` and `strict`. protovalidate-es's native header-name pattern
  contains the range `+-.`, which admits `,`; the CEL in `validate.proto` puts
  `-` last, as a literal. Rather than pick one, the rule is left to
  protovalidate;
- `string.not_in`, `string.not_contains`, int32-family `not_in`;
- an int32-family range read inside out (`gt` above `lt`), which chained checks
  cannot say;
- every 64-bit integer, `float`, `double` and `bytes` rule;
- every `map` rule, `keys` and `values` included, and `repeated.unique`;
- rules on a message-typed field: Timestamp, Duration, Any, FieldMask, wrappers;
- field CEL;
- every rule of a field with `ignore` set, or of list items with
  `repeated.items.ignore` set. Those get no native check at all. A member of a
  `(buf.validate.message).oneof` counts as `IGNORE_IF_ZERO_VALUE`, which is what
  protovalidate gives it;
- `enum` rules on `google.protobuf.NullValue`, whose JSON form is `null` rather
  than a member name.

`required` keeps its mandatory key under every `ignore` but `IGNORE_ALWAYS`, as
protovalidate keeps the rule.

A message-typed value under `ignore = IGNORE_ALWAYS` (the field's, the list
items' or the map values') is `z.unknown()`, and its doc comment says so:
protovalidate never evaluates the message inside, and the message's own schema
would apply its rules. Its `field()` still checks the value decodes, as
protojson does. It is the one place the Zod input is wider than protobuf-es's
JSON type, and `make verify` lists it as such.

### How `field()` and `message()` work

`strict/protovalidate.ts` imports `@bufbuild/protobuf` and
`@bufbuild/protovalidate`, not `zod`. A refinement needs only
`ctx.addIssue({ code: "custom", message, path, params })`, which both Zod majors
accept, so one module serves both targets. One validator serves every schema;
protovalidate plans each message type once.

**`field(desc, name, native)`** refines one field's schema:

1. `fromJson(desc, { [jsonName]: value })` builds a message with only that
   field set.
2. `validator.validate(desc, msg)` runs protovalidate over it.
3. It keeps the violations whose field path starts at this field and continues
   only through list indexes and map keys. A path into a nested message belongs
   to that message's own schema.
4. It drops the violations of the rules in `native`, which the Zod checks
   already report, so a failure is reported once.
5. Each kept violation becomes a `custom` issue with protovalidate's message, a
   path below the field, and `params: { ruleId }`.

A `fromJson` failure becomes one issue. A validator error does not: every other
field of the sparse message holds its zero value, and a CEL rule elsewhere may
fail to evaluate on it (`this.tags[0]` on an empty list) though the full
message is valid, so it is left to `message()`, which then also reports this
field's violations. `field()` throws at import time if the descriptor has no
field of that name.

**`message(desc)`** refines `<message>Zod`:

1. `fromJson(desc, value)` over the whole value. If it throws, it adds one issue
   at the field whose value does not decode, unless that field's `field()` or
   nested `message()` reports it already; at the message itself when no single
   field is to blame, as when two members of a oneof are set.
2. `validator.validate(desc, msg)`. A validator error becomes one issue.
3. It keeps what no field schema sees:
   - violations without a field path: message CEL and
     `(buf.validate.message).oneof`;
   - violations rooted at a oneof: `(buf.validate.oneof).required`;
   - violations on a field absent from the input, except `required`, which the
     object already enforces with a mandatory key.

   Violations on a present field are skipped. `field()` or a native check has
   already reported them, unless the field's sparse message failed to evaluate.

**Absent implicit fields.** protojson omits a zero value, so an `Address` whose
`country` is `""` arrives as `{}`. protovalidate still validates the `""`, and
`string.len = 2` rejects it. `<message>ZodObject` never sees the key, so only
`message()` can report it: `addressZodObject.parse({})` succeeds,
`addressZod.parse({})` fails on `country` and `postalCode`. The doc comment of
`<message>Zod` names these fields:

```ts
/**
 * Full validation of example.v1.Address. Adds what protovalidate checks on the whole message:
 *   the rules of country, postal_code when absent: protojson omits a zero value
 */
export const addressZod = addressZodObject.superRefine(message(AddressSchema));
```

Issue paths use JSON names, with oneofs flattened as in JSON, list indexes as
numbers and map keys as strings.

**`register(file)`**, called by every `.zod.ts` and `.zod3.ts` for its own file,
adds the file's types and its imports' to the registry `fromJson` decodes with,
so an `Any` packing any type an imported module declares decodes.

**Cost.** Parsing costs one sparse `fromJson` and validation per field that
carries `field()`, plus one full validation per message that carries
`message()`. A nested `<message>Zod` with `message()` validates its whole
subtree again, so a deep payload costs about its size times its depth.

**What cannot be checked is not rejected.** A `fromJson` failure for an `Any`
whose type no imported module registered, and a protovalidate compilation
error (a predefined rule whose extension the validator was not given), say
nothing about the value. Both add no issue: under-narrowing is the safe
direction.

**Why protovalidate-es, not a copy of its checks.** Its `isHostname`, `isUri`
and the rest are not exported, and a copy would be a second implementation to
keep in step. Its `createStandardSchema` builds the message from the init shape,
not from JSON, so its issue paths use local names and a `oneof.value` segment
JSON does not have.

### Recursion

A message cycle always sits inside one file: proto imports cannot be cyclic,
so neither can the modules. The generator writes a file's messages
dependencies first, and defers a reference only inside a cycle.

- **Zod 4**: a getter in `z.strictObject`, which keeps `.shape` and the inferred
  type:

  ```ts
  export const treeNodeZodObject = z.strictObject({
    label: z.string().min(1).optional(),
    get children() {
      return z.array(treeNodeZod).optional();
    },
    get parent() {
      return treeNodeZod.optional();
    },
  });
  ```

- **Zod 3**: no type is inferred through a getter. The other fields go in a
  `<message>Base` object, spread next to the fields of the cycle, each a
  `z.lazy()`, and a structural `<Message>Shape` types the lazies. Types stay
  exact, and `.shape`, `.pick()` and `.extend()` keep working:

  ```ts
  const treeNodeBase = z.strictObject({
    label: z.string().superRefine(field(TreeNodeSchema, "label")).optional(),
  });

  type TreeNodeShape = z.input<typeof treeNodeBase> & { children?: TreeNodeShape[]; parent?: TreeNodeShape };

  export const treeNodeZodObject = z.strictObject({
    ...treeNodeBase.shape,
    children: z.array(z.lazy((): z.ZodType<TreeNodeShape> => treeNodeZod)).optional(),
    parent: z.lazy((): z.ZodType<TreeNodeShape> => treeNodeZod).optional(),
  });
  ```

### `zod` and `zod3` side by side

| Aspect | `zod` (4.6) | `zod3` |
|---|---|---|
| Module | `<file>.zod.ts`, `strict/wkt.zod.ts` | `<file>.zod3.ts`, `strict/wkt.zod3.ts` |
| Import | `import { z } from "zod"` | `import { z } from "zod/v3"`, in zod@^3.25 and zod@^4 |
| `string.min_len`, `max_len`, `len` | native | `field()` |
| A message in a cycle | getters: `.shape` and types kept | a base object, spread next to typed `z.lazy()` fields: `.shape` and types kept |
| A field with `field()` | `ZodString`, the check inside | `ZodEffects<ZodString>`; `.innerType()` reaches the string |
| A refined `<message>Zod` | `ZodObject` with a refinement: `.shape` works, `.pick()` throws | `ZodEffects`, no `.shape` |
| `Value`, `Any` | `z.json()`, `z.looseObject` | a `z.lazy()` union, `.passthrough()` |

## Before you rely on it

- **`json` covers top-level messages only**, because protoschema-jsonschema
  bundles nothing else. The Zod targets cover every message.
- **The JSON Schema carries no CEL, no oneof and no rule of an absent field.** A
  missing key on an implicit field is the zero value to protovalidate, and the
  schema accepts it: `{}` passes `addressJsonSchema`, though protovalidate
  rejects the empty `country`. The doc comment names those fields under
  "absent fields".
- **Registry.** `fromJson` needs a registry to decode an `Any` that has an
  `@type`. Every `.zod.ts` and `.zod3.ts` calls `register(file_<path>)`, which adds its file's
  types and those of its imports to the one registry `strict/protovalidate.ts`
  parses with, so an Any of a type any imported module declares decodes. Any
  other Any is not checked: `fromJson` cannot decode it, and the refinement adds
  no issue. protovalidate-es also takes a registry, for user-defined predefined
  rules; `strict/protovalidate.ts` passes none, so such a rule is a compilation
  error, and is not checked either.
- **Looser than protobuf-es where nothing parses.** `Timestamp`, `Duration`,
  `FieldMask` and `bytes` are `z.string()`, and `z.number().int()` does not
  check the 32-bit range. `fromJson` checks them only inside `field()` or
  `message()`, so a composed schema, or a `<message>Zod` that is its
  `<message>ZodObject`, does not: `wellKnownCoverageZodObject` accepts
  `{ "createdAt": "yesterday" }`, which `wellKnownCoverageZod` rejects.
- **`lt_now`, `gt_now` and `within`** evaluate against the client's clock.
- **The Zod targets add weight to a client bundle**: protovalidate-es, and
  through it `@bufbuild/cel` and `@bufbuild/re2`.
- **Proto2 `required` is not checked.** The validator runs with its defaults,
  without `legacyRequired`.
- **Extensions are not modelled.** Their `[name]` keys fail `z.strictObject`.
